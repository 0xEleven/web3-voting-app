1. Executive Summary & Problem Statement

1.1 Centralized Voting Vulnerabilities

Traditional electronic voting systems and physical ballot operations rely on centralized authorities and mutable database architectures. These systems exhibit three primary structural vulnerabilities:

  • Opaque Ballot Storage: Voters have no mechanism to mathematically verify that their vote was recorded accurately without trusting an intermediary database administrator.
  • Double-Voting and Ledger Tampering: Centralized databases (e.g., PostgreSQL, MySQL) allow administrative overrides, SQL injections, or unlogged data mutations that cannot be independently audited by third parties.
  • Single Point of Failure: Centralized electoral servers can be targeted with distributed denial-of-service (DDoS) attacks, unscheduled outages, or forced state rollbacks during active voting sessions.

1.2 The Decentralized Web3 Guarantee

This project eliminates centralized trust by deploying an autonomous, immutable voting protocol directly to the Ethereum Virtual Machine (EVM). Every ballot cast constitutes a cryptographically signed transaction signed by the voter's private key via ECDSA (secp256k1) and permanently anchored to the distributed ledger.

  • Cryptographic Immutability: Once confirmed inside an Ethereum block, ballot state cannot be overwritten, modified, or reordered by any party, including the contract deployer.
  • Strict Single-Vote Invariant: An on-chain mapping table provides constant-time O(1) verification, reverting duplicate transactions before state alteration occurs.
  • Administrative Transparency: All lifecycle events (e.g., candidate registration, session pause/resume) emit immutable EVM logs accessible to all network observers in real time.

3. Smart Contract Formal Specification (contracts/Voting.sol)

3.1 Data Structures & Storage Layout

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract Voting {
    struct Candidate {
        uint id;
        string name;
        uint voteCount;
    }

    address public owner;
    uint public candidatesCount;
    bool public votingActive = true;

    mapping(uint => Candidate) public candidates;
    mapping(address => bool) public hasVoted;

    event Voted(uint indexed candidateId, address indexed voter);
    event CandidateAdded(uint indexed candidateId, string name);
    event VotingStatusChanged(bool active);
}

3.2 State Variable Slot Architecture

Variable Type Slot Allocation Description & Security Considerations
owner address Slot 0 (20 bytes) Stores the contract deployer address. Used by onlyOwner modifier.
votingActive bool Slot 0 (1 byte packed) Boolean circuit breaker. Packed with owner into Slot 0 to minimize gas storage overhead.
candidatesCount uint256 Slot 1 (32 bytes) Tracks total registered candidate nominees. Incremented monotonically.
candidates mapping(uint => Candidate) Slot 2 (Hash Pointer) Stores candidate records keyed by candidate ID. Values located at keccak256(key . slot).
hasVoted mapping(address => bool) Slot 3 (Hash Pointer) Maintains the registry of voter addresses that have cast ballots. O(1) lookup.

4. Security Architecture & Threat Model

The smart contract implementation has been hardened against common Ethereum security vulnerabilities:

Vulnerability Vector Risk Level Mitigation Mechanism Verification Outcome
Double-Voting Attack Critical Strict O(1) state registry check: require(!hasVoted[msg.sender], "Already voted!"). Mapping is updated before any event logs. Verified by automated unit test test/Voting.test.js line 53. Duplicate transaction reverts.
Privilege Escalation High Custom onlyOwner modifier strictly validating msg.sender == owner for candidate registration and status changes. Non-owner calls revert with "Only owner can perform this action".
Out-of-Bounds Ballot ID High Explicit range assertion: require(_candidateId > 0 && _candidateId <= candidatesCount). Reverts with "Invalid candidate" for candidate ID 0 or arbitrary large integers.
Reentrancy Exploitation Low Strict adherence to the Checks-Effects-Interactions pattern. The contract transfers no native Ether and executes zero external contract calls. Immune to reentrancy vectors. State writes are atomic.
Arithmetic Overflow / Underflow Negligible Solidity version ^0.8.20 includes default compiler-level checked arithmetic for all unsigned integers. Automatic reverts on overflow boundaries without external library dependencies.
Denial of Service (DoS) Low Candidate counts are bounded in practice. Individual voting transactions write to isolated storage slots with constant gas overhead (~48,000 gas). No unbounded storage loops exist in state-mutating execution paths.

6. Frontend Engineering & Client Architecture

6.1 Reactive Web3 State Synchronization

The client interface (located in frontend/src/App.jsx) uses React 18 hooks coupled with Ethers.js v6. The frontend continuously monitors wallet connectivity and contract state:

  • Provider Initialization: Connects to window.ethereum using ethers.BrowserProvider, requesting active accounts via eth_requestAccounts.
  • Network Awareness: Detects Chain ID dynamically (Localhost 31337 vs. Sepolia 11155111) and prompts the user to switch networks using the header action buttons.
  • WebSocket Event Subscriptions: Automatically attaches event listeners to votingContract.on("Voted", ...), votingContract.on("CandidateAdded", ...), and votingContract.on("VotingStatusChanged", ...) to synchronize UI counters across multiple voter terminals in real time.

6.2 Cryptographic Voter Receipt Subsystem

Upon successful transaction confirmation on the Ethereum blockchain, the application computes and displays an immutable digital receipt containing:

Voters can copy this JSON payload with a single click to audit their transaction on Etherscan or local block explorers.

6.3 Interactive Simulation Fallback Mode

To ensure seamless evaluation in environments where MetaMask is unavailable (e.g., standard browser without Web3 extensions), the application automatically detects the absence of window.ethereum and falls back to an in-memory interactive simulation mode. Evaluators can cast votes, test double-vote rejection guards, filter candidates, and test returning officer controls without blockchain configuration hurdles.

8. Deployment & Operational Runbook

8.1 Local Development Workflow

# Step 1: Install root project dependencies
npm install

# Step 2: Run automated test suite (13 passing tests)
npm test

# Step 3: Start the local Ethereum JSON-RPC node
npm run node

# Step 4: Deploy smart contract to the local node (separate terminal)
npm run deploy:local

# Step 5: Launch the React frontend application
npm run dev

The application will be accessible at http://localhost:3000 or over the local area network at http://192.168.100.7:3000.

8.2 Sepolia Ethereum Testnet Deployment

# 1. Create .env file with your Sepolia private key and RPC URL:
SEPOLIA_RPC_URL="https://rpc.sepolia.org"
SEPOLIA_PRIVATE_KEY="0xYOUR_TESTNET_PRIVATE_KEY"

# 2. Deploy smart contract to Sepolia:
npx hardhat run scripts/deploySepolia.js --network sepolia

The deployment script automatically synchronizes the deployed address and ABI to frontend/src/contracts/contractData.json, enabling instant frontend interaction on the live testnet.
